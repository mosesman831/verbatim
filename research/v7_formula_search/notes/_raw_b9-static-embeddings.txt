## TL;DR

A learned static embedding table is a strict upgrade over `hashing:subword-ngram:v1` as Verbatim's dense lane: same "local, deterministic, no-network, hash-pinnable artifact" properties, encode cost in the tens of microseconds (measured 11 µs/query here; vendor CI ~8 µs), and a real semantic lift — trained static tables reach ~72–82% of all-MiniLM-L6-v2's MTEB-retrieval score while hashing can only ever reflect shared subwords (measured: a vocabulary-disjoint paraphrase scores ~+0.15 cosine — the collision noise floor — vs +0.97 for a lexical match). Recommendation: **ship `potion-retrieval-32M` (MIT, 63,091×512) or `potion-base-8M` (MIT, 29,528×256) as a hash-pinned artifact for the dense lane in the default profile**; keep hashing as a zero-cost lexical sub-lane; defer a small ONNX bi-encoder to the "quality" profile.

## 1. Candidates and exact formulas

### 1.1 Model2Vec / Potion encoding formula (inference path)

Verified in `model2vec/model.py` (`StaticModel._encode_batch`, `tokenize`, `_encode_helper`):

```
ids      = WordPiece(text, add_special_tokens=False)[:max_length]   # max_length=512 default
ids      = [i for i in ids if i != UNK_ID]                          # UNK dropped, not mapped
e(text)  = (1/|ids|) * Σ E[id]                                      # plain mean of table rows
if normalize:  e ← e / (||e||₂ + 1e-32)
```

- Table `E` is `vocab × d` float32 on disk (potion models ship F32 safetensors).
- `weights`/`token_mapping` only exist for vocab-quantized models; all flagship potion models ship `has_weights=false, has_token_mapping=false` (verified in their integration baseline JSONs).
- Batch fast path: sentences grouped by length → single `E[id_matrix].mean(axis=1)` gather.
- No attention, no matmul at query time. A lookup table + averaging. `EmbeddingBag(30522,1024,mode='mean')` is the identical construction in the sentence-transformers static models.

**Important correction to a common misread**: PCA and SIF are **build-time** transforms baked into the stored table. Query-time cost is just tokenize → gather → mean → L2. There is no projection at inference.

Worked example (query `"what is hashing"` → ids `[2054, 2003, 24204]` on a 29,528×256 table):
- Gather: `E[[2054,2003,24204]]` → 3×256 rows (~3 cache-miss-ish lookups, 3 KB read)
- Mean: 768 adds, 256 divides
- L2: 256 squares + sqrt + 256 divides → total ≈ 1.3 kFLOP + one tokenize.

### 1.2 Distillation recipe (M2V_base_* models) — exact constants

From `model2vec/distill/distillation.py` + `model2vec/distill/inference.py`:

1. Per token `t` in vocab (after dropping `\[unused\d+\]` — BERT vocab 30,522 → 29,528): forward pass through teacher (bge-base-en-v1.5), **masked-mean** pool the last hidden state → raw vector `x_t` (768-d).
2. `compute_weights(n, a)`: Zipf proxy `p_i = (1/(i+1)) / Σ_j (1/(j+1))`, i.e. rank-i token gets harmonic-probability; SIF weight `w_i = a/(a + p_i)`. **Code default `sif_coefficient = 1e-4`** (`distill_from_model` signature). NB: the docs/blog show `10⁻³/(10⁻³+p)` — the docstring and doc site disagree with the current default; treat a as tunable in [1e-4, 1e-3].
3. `apply_pca(E, 256)`: center by column-mean, eigendecompose the covariance (`np.linalg.eigh`), take top-k components, project `Xc @ Vᵀ`, sign-flip components so their max-|score| loading is positive. **PCA helps even at full rank** (ablation: no-PCA costs −3.0 avg-MTEB pts: 45.34→42.31), i.e. it whitens/normalizes the space, not just shrinks it.
4. `E ← PCA(E) ⊙ w` (weights multiplied per-row at build time), then quantized — distill default `quantize_to=Float16`.
5. `normalize=True` written to config.

### 1.3 Potion recipe (the trained models — tokenlearn, MIT)

From the model card + `tokenlearn/train.py`:
1. distill (as above) → initial static model;
2. featurize: teacher mean-embeds a large corpus (C4-en) → target sentence vectors;
3. train the **embedding table** by MSE against teacher vectors (`freeze_weights=True` → per-token weight vector `w` stays all-ones, pooling is a plain mean during training; only `E` is learned);
4. post-training re-regularization: frequency weighting → PCA → SIF.
5. `potion-retrieval-32M` is `potion-base-32M` **fine-tuned on retrieval pairs** (gooaq, msmarco triplets, squad, s2orc, all-nli, paq, trivia-qa, msmarco-10m, swim-ir, pubmedqa, miracl, mldr, mr-tydi).

So "potion" = learned static table, not merely a distilled cache; that training is why it beats M2V_base_output by +5.75 MTEB-retrieval points at the same dims.

### 1.4 sentence-transformers static-retrieval-mrl-en-v1 (Apache-2.0)

- `EmbeddingBag(30522 × 1024, mean)` with bert-base-uncased WordPiece; trained from scratch with MultipleNegativesRankingLoss + MatryoshkaLoss on 30 QA/retrieval datasets (deliberately disjoint from BEIR so NanoBEIR is zero-shot).
- Matryoshka: dims are nested — truncate columns to 512/256/128/64; NanoBEIR nDCG@10: 1024→0.5032, 512→0.4957 (−1.5%), 256→0.4819 (−4.2%), 128→0.4622, 64→0.4176.
- 100–400× faster than mpnet on CPU (measured 397×); no max sequence length; linear in token count.

### 1.5 GloVe mean-pool

`e(text) = mean_{w∈text} G[w]` over a word-level vocab (glove.6B.300d: ~400k words × 300d). OOV tokens skipped. No subword fallback → brittle on rare words; this is why the whole-word GloVe rows underperform even BM25 on NanoBEIR (0.3293 vs 0.4518).

### 1.6 model2vec int8 quantization (exact code)

`model2vec/quantization.py::quantize_embeddings`: **single global scale** `s = max|E|/127`; `Q = clip(rint(E_f16/s), −127, 127) → int8`. At inference, `E8[ids]` is cast up to f32 before pooling (dtype promoted in `_encode_batch`). Also available: `dimensionality=d` (slice first d columns — valid because PCA/MRL dims are ordered) and `vocabulary_quantization=k` (k-means over normalized rows → centroid table + token_mapping + per-token norm weights).

## 2. Per-query cost on the 4-core reference machine

Encode is `O(T·d)` gather+mean; exact-scan candidate generation is `O(N·d)` dot products. Measured on this 8-core box (numpy 2.2, fp32), scaled ×~2–4 for a slower 4-core target:

| op | arithmetic | measured (8c) | est. 4-core |
|---|---|---|---|
| encode query, T=12, d=256 | 12 gathers + 3.1k flops | 10.9 µs | ~0.02–0.04 ms |
| encode memory, T=60, d=256 | 60 gathers + 15k flops | 14.8 µs | ~0.03–0.06 ms |
| encode, pure-Python dict (no numpy) | same, scalar loop | 187 µs | ~0.4–0.8 ms |
| scan, N=10k, d=256 f32 | 2.56M MAC, 10MB read | 0.079 ms | ~0.2 ms |
| scan, N=100k, d=256 f32 | 25.6M MAC, 102MB read | 1.41 ms | ~3–5 ms |
| scan, N=100k, d=512 f32 | 51.2M MAC, 205MB read | 2.33 ms | ~5–8 ms |

Tokenizer (HF `tokenizers`, WordPiece): vendor CI logs 1.57M tokens/s end-to-end including encode — ~0.6 µs/token; ~8 µs for a 12-token query. A pure-Python greedy-longest-match WordPiece is ~150 lines and lands ~100–300 µs/query — still irrelevant next to search p50=46 ms.

For comparison, MiniLM-L6-v2 ran 1,739 sent/s on a 16-core i7-13700K (~0.6 ms/query there, ~2–5 ms/query on 4 cores) — also inside budget but ~50–150× the encode cost of the table, plus onnxruntime + ~23–90 MB artifact.

## 5. Does a static table beat hashing subword-ngrams on paraphrase?

No published head-to-head of blake2b-subword-hashing vs learned static tables exists — marking that honestly. The evidence is three-sided:

1. **Mechanism (structural, not empirical)**: hashing is a Johnson–Lindenstrauss random projection of the *lexical* feature vector — it preserves inner products of ngram-bag representations up to collision noise but has no cross-term similarity: two disjoint-vocabulary paraphrases can only collide by accident. A learned table places synonyms near each other because the teacher saw them in similar contexts.
2. **Published proxy**: on NanoBEIR, trained static (0.5032) beats the best *lexical* baseline BM25 (0.4518) by +11.4% relative, and BM25 is strictly stronger than hashing (real IDF, no collisions, no dimension cap). On paraphrase-heavy NanoQuoraRetrieval, static-retrieval hits 0.8951 nDCG@10.
3. **My measured demo** (pure-Python blake2b 3–5-gram hashing, d=1024): same-words pair cos = **+0.972**; paraphrase sharing only "the" = **+0.317**; disjoint-vocab pairs over 291 samples = **+0.154 ± 0.114** (max 0.575) — i.e. a real paraphrase scores *inside the collision noise band*, orders of magnitude below the ~0.7–0.9 a learned table gives semantic equivalents.

Verbatim's open-domain gap (0.196 vs BM25 0.370 any@10) is exactly the regime hashing cannot address: queries whose evidence shares no ngrams with the question. A trained static lane is the cheapest fix that preserves every hard rule: the table is a hash-pinned local artifact (SHA256 the safetensors + tokenizer.json), deterministic, non-generative, and only ever produces **candidates** — byte-pin and eligibility run unchanged downstream ("approximate candidate generation is allowed; approximate authorization is not"). Embeddings live in the background write path, which keeps Add-ack model-free.

## 6. Where it lands in the pipeline

- **Replaces/augments**: the `dense/sparse-semantic` lane (candidate generation only). Nothing else changes — eligibility, RRF k=60 fusion, boosts all apply as designed; the static vector is just a much better candidate generator than hashed ngrams.
- **Write path**: background embed job on memory write (60-token turn ≈ 0.03 ms) — consistent with "embedding is a background job".
- **Encoder id**: e.g. `static:potion-retrieval-32M:f32:v1` — versioned like `hashing:subword-ngram:v1`; multiple lanes can coexist under RRF.
- **Tokenizer dependency**: potion/static-retrieval need the bge/BERT-uncased WordPiece vocab (~460 KB vocab.txt; or ~2–4 MB tokenizer.json). Implementable dependency-free (~150 lines, deterministic) or pin the `tokenizers` wheel.
- **Caveat**: potion + static-retrieval-en are **English-only**. If Verbatim ingests non-English turns, either keep hashing for those rows or use `potion-multilingual-128M` (MIT; MMTEB Ret 37.86) / `static-similarity-mrl-multilingual-v1` (Apache-2.0; Ret 41.21 — actually beats LaBSE's 33.17 on retrieval).

The single biggest open uncertainty is *domain*: LoCoMo-style conversational turns are short, first-person, entity-dense — neither MTEB-Ret nor NanoBEIR is that distribution; the cheapest calibration is re-running the existing eval harness with `potion-retrieval-32M` and `static-retrieval-256` as candidate lanes. If the delta vs hashing is <3 pts any@10, revisit — but the mechanism says it won't be close. A small ONNX bi-encoder becomes the default only if dense-lane weight in RRF ends up dominant AND the +12–25% headroom survives an A/B on the memory corpus.

## UNRESOLVED

- No published *direct* paraphrase benchmark of raw feature-hashing vs static tables (e.g. PAWS/QQP with a hashing encoder). Would close it by running both encoders on QuoraRetrieval/PAWS in the eval harness — cheap, no downloads needed beyond the table artifact.
- Exact SIF coefficient used in released potion builds (docs say 1e-3, code default now 1e-4, tokenlearn applies it inside re-regularization) — only relevant if Verbatim self-distills; irrelevant when shipping a prebuilt artifact.
- int8 quality delta on a *retrieval* metric (vs. my 0.9999 reconstruction cosine): model2vec claims "minimal performance loss" without publishing an int8 MTEB row; validate by spot-scoring the eval set after quantizing.
