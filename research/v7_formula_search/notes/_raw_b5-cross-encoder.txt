## 0. TL;DR

A cross-encoder (CE) is the cheapest "semantic" signal Verbatim can buy without changing
the default no-network, no-model-download install — *if* it is kept off the default path.
On a generic 4-core client CPU, the only CE that plausibly fits inside the stated
"≤150 ms total with a small one" budget at a useful pool depth is
`cross-encoder/ms-marco-TinyBERT-L2-v2` (~4 MB int8, ~1–3 ms/pair at seq≤128 →
~35–90 ms for a pool of 32). The best quality-per-watt pick is
`cross-encoder/ms-marco-MiniLM-L6-v2` (~22 MB int8, ~10–15 ms/pair → ~350–500 ms
at pool 32): it must live behind a `max` profile or a pool of ≤8–12 inside `quality`.
Everything ≥150 M parameters (bge-base/large, gte-modernbert, mxbai-base, jina-v2/v3,
zerank, Qwen-rerankers) is a CPU reject at 4 cores. Licenses rule out all Jina v2+
rerankers (CC BY-NC 4.0). Expected any@10 gain over BM25-only is **extrapolated**
+3–7 pts for MiniLM-L6-class, +1.5–4 pts for TinyBERT-L2 at pool 32.

**Single most important number established:** per-pair CE scoring cost on CPU is
~`F = P_enc·2·T + 4·L·d·T²` FLOPs; at T=128, MiniLM-L6 ≈ 2.9 GF → **~10–15 ms/pair**
(measured 95 pairs/s int8 on a 6-core AVX2 i7-9750H) — so a pool-32 rerank costs
~0.4 s on the reference machine, which is *outside* the 150 ms quality budget and
decides the whole verdict structure.

---

## 1. What a CE is and where it sits in Verbatim

A cross-encoder scores `(query, memory)` pairs jointly: input `[CLS] q [SEP] m [SEP]`,
one forward pass, one scalar logit. Pointwise (classification) CEs dominate the
sub-300M range; MonoT5-style seq2seq models decode a "true" token; listwise models
score a whole list in one context.

**Verbatim stage:** this is the *optional rerank* stage in the stated pipeline
(query analysis → lanes → eligibility → fusion → **rerank** → pack). It does not
touch lanes, eligibility, byte-pins, or the pack — it only reorders an eligible,
fused pool. That makes it fully compatible with the hard rules: eligibility stays
exact (applied upstream), and the CE emits no text, so no byte-pin is needed.
Recommendation: rerank pool `P = 32` from RRF fusion, final order by CE logit with
the fused score as tiebreaker (or `score = α·z(fusion) + (1−α)·σ′(CE)`, α≈0.3–0.5);
CE score may optionally feed back as a "proof" signal but that is a separate
question (b-series fusion).

**Key sizing fact for the index question:** a CE stores *zero bytes per memory*.
It is a fixed resident artifact (model weights) of 4–560 MB — nothing is indexed
per memory, nothing precomputed at write time. The write path is untouched.

## 2. Cost model (the formula + constants)

For an encoder-only CE with hidden `d`, intermediate `i`, layers `L`, pair length `T`:

```
FLOPs/pair ≈ L·(8d² + 4·d·i)·T   +   L·4·d·T²
            ── projections+FFN ──    ── attention QKᵀ/AV/softmax ──
```

Quadratic share = `T / (6d + T)`:
d=384 → T=64: 2.7 %, T=128: 5.3 %, T=256: 10 %, T=512: 18 %.
**⇒ latency is ~linear in pair token-length up to T≈256** (at T=512 ~20 %
superlinear). Truncating pairs 256→128 almost exactly halves cost; this is the
only meaningful latency lever — you cannot "hash" inputs into a CE (it needs raw
token interaction, unlike the blake2b-ngram embedder).

MonoT5-style: `F ≈ L_e·(8d²+4di)·T (enc) + L_d·(12d²+4di)·~2 tok (dec) + 2d·vocab (LM head)`
→ encoder-dominated but pays an extra decode+head step (~10 % overhead).

Effective CPU throughput used for conversion (calibrated, not invented):
- **Conservative 4-core AVX2 (reference machine): ~200–270 GFLOPS int8** — anchored to
  temsa's measured 95 pairs/s for MiniLM-L6 int8 on i7-9750H ⇒ 2.87 GF / 10.5 ms ≈ 273 GFLOPS.
- **Optimistic 4-core AVX-512-VNNI: ~400–600 GFLOPS int8** (boxed CPUs since ~2021;
  consistent with clouatre's ~2 ms/pair on MiniLM-L12).
- My own box measures 640–780 GFLOPS fp32 BLAS (Xeon 8559C, 4 threads); real CEs run
  ~30–50 % of GEMM peak (attention/LN/softmax/memory), consistent with the above.

Tokenizer+overhead ≈ 0.3–1 ms/pair (wordpiece/BPE on CPU, one pair at a time).
Batching pairs (batch 8–32) amortizes to ~0.7–0.9× the sequential per-pair cost.

Worked example — MiniLM-L6 @T=128 (d=384, i=1536, L=6):
`6·(8·384² + 4·384·1536)·128 = 6·(1.18M + 2.36M)·128 = 2.72 GF` linear
`+ 6·4·384·128² = 0.15 GF` attention ⇒ **2.87 GF/pair**;
@270 GFLOPS → **10.6 ms/pair**; pool 32 → **~340 ms** (batch-eff ~0.9 → ~310 ms).
Matches temsa's measured 210 ms/20-pair request = 10.5 ms/pair within 5 %.

## 4. Per-query time on the 4-core reference (arithmetic shown)

CE cost per query = `P · t_pair(+tokenizer) / batch_eff`, **independent of N** —
a CE has no per-memory index or precomputation, so 10k and 100k memories cost
identically (only upstream candidate generation scales with N; BM25 sub-linear).

`budget_CE ≈ P·t·0.85 (batch) + 0.5·P·0.3ms (tok)`.

|---|---|---|---|---|
| TinyBERT-L2-v2 | ~1.5–3 / ~0.5–1 | ~25–50 | ~40–90 | ~80–170 |
| MiniLM-L2-v2 | ~4–6 / ~2 | ~70–100 | ~110–165 | ~220–330 |
| MiniLM-L4-v2 | ~8–12 / ~4 | ~140–200 | ~220–330 | — |

mxbai-xsmall ~70 MB; gte-modernbert ~150 MB; bge-base ~280 MB. **0 B/memory.**

## 5. Expected Verbatim gain (extrapolated — flagged)

- Evidence recall headroom on the measured set: BM25 any@10 0.596 vs any@20 0.677
  (+8 pts in the pool). A CE reorders *inside* the pool and adds paraphrase/
  semantic discrimination the lexical fusion lacks.
- Published over-BM25 deltas at pool 100–1000: +5.6 (MiniLM BEIR indep) to +9.9
  (monoT5-3B) nDCG@10; MS MARCO MRR +14–20 pts. Pool-32 retains ~85–97 % of
  pool-100 gains per the @50/1000 datapoint. Conversational, informal LoCoMo text
  is *out-of-domain* for MS MARCO-trained CEs — Rosa et al. show in-domain
  effectiveness overstates zero-shot, so haircut the delta.
- **Extrapolated any@10 gain over BM25-only at pool 32: TinyBERT-L2 +1.5–4 pts;
  MiniLM-L6 / jina-turbo +3–7 pts.** Confidence: medium-low — needs one LoCoMo
  eval run to pin down (any CE eval on the existing harness closes this).

swappable alternative pending a LoCoMo bake-off. Default profile: **no CE**.

## 7. Implementation notes for the synthesis engineer

- ONNX artifacts are official for the ms-marco family (`onnx/model_qint8_avx512_vnni.onnx`,
  `model_quint8_avx2.onnx`), jina-v1 (`onnx/model_int8.onnx`), mxbai-v1, gte-modernbert,
  bge-v1 (fp32 only — quantize locally). MonoT5/InRanker need Optimum export.
- Fix a pair token budget `T_cap = 128` (query + memory + specials; LoCoMo-class turns
  are ~10–60 tokens) — cost is ~linear in T; padding to 512 wastes ~4×.
- Score cache: `H(query_norm, memory_id) → logit` — queries repeat; CE result is
  deterministic, cacheable like any derived signal (no byte-pin issue, it stores
  a float, not text).
- Do **not** let CE output create facts — reorder only; add-ack stays model-free.
- Batch all pool pairs through one ORT call; pin `max_length` to T_cap to get the
  batching discount.
